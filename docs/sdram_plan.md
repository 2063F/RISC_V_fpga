# SDRAM 実装計画

ロードマップ Phase 10 (SDRAM) の進め方。今のメモリは FPGA 内蔵の BSRAM だけ
(命令 ROM 32 KB・データ RAM 32 KB、BSRAM 56 ブロック中 36 を使用) で、
オセロでも ROM 23 KB を使い、残りは少ない。外付け SDRAM で数十 MB のメモリを足す。

## ゴール

1. **最初のゴール:** SDRAM をデータ用メモリとして使えるようにする。
   2 つのハートから普通のロード/ストアとアトミック命令で読み書きでき、
   C から大きな配列 (例: オセロ AI の置換表) を置ける
2. **その先 (任意):** SDRAM 上のプログラムを実行する。
   UART でプログラムを SDRAM に送って起動するブートローダを作れば、
   プログラムを変えるたびに合成し直さなくて済む

## Phase 0: ハードウェアの確認 (最初にやる。作業はユーザー)

ここが決まらないと先に進めない。

| 確認すること | 理由 |
|:--|:--|
| 使う SDRAM モジュール (Sipeed の TANG_SDRAM か) と、そのチップの型番 | タイミングのパラメータ (tRCD, tRP, tRC, CAS レイテンシ, リフレッシュ間隔) をデータシートから取る |
| チップ構成: 2 チップが共通アドレスで 32 ビット幅になるか、16 ビット 1 チップずつか | 1 ワードを 1 回で読めるか、16 ビット × 2 回 (バースト長 2) かが変わる |
| モジュールをつなぐコネクタ (Dock の 40 ピンヘッダの見込み) と、その FPGA ピン名 | 今のピンと重なるかを見る |
| 今の周辺のピン (キーボード 16・LED マトリクス 24・VGA 5・USB 2) が、そのコネクタを使っていないか | **重なる可能性が高い**。SDRAM は 16 ビット 1 チップでも約 39 本要る |

ピンが重なる場合の選択肢:

- **A. 周辺を減らす:** LED マトリクスをシフトレジスタ (74HC595 など) 経由にして 24 本 → 3〜4 本、
  キーボードもシフトレジスタか I/O エキスパンダにする (回路の作り直しが要る)
- **B. 展示用と SDRAM 用で構成を分ける:** SDRAM の開発中はキーボードや LED マトリクスを外し、
  合成の設定 (`fpga_top` のパラメータか別トップ) で切り替える
- **C. 別の空きピンへ移す:** PMOD など、SDRAM と重ならないピンが足りる場合だけ

## 全体の方針 (推奨)

| 項目 | 推奨 | 理由 |
|:--|:--|:--|
| アドレス | `0x2000_0000` から (容量分) | 今の ROM `0x0000_xxxx`・RAM `0x0001_xxxx`・MMIO `0x8000_xxxx` と重ならず、上位ビットだけで判定できる |
| クロック | 最初は CPU と同じ 50 MHz | クロック乗せ換えが要らない。50 MHz なら CAS レイテンシ 2、tRCD・tRP は 1 クロックで済む見込み (データシートで確認) |
| SDRAM へのクロック | PLL で位相をずらした 50 MHz を出す (`gowin_pll_usb` と同じ作り方) | 入出力のセットアップ・ホールドを確保する。位相は実機で調整できるようにパラメータにする |
| コントローラ | 自作。1 回の要求ごとに ACTIVE → READ/WRITE (オートプリチャージ付き) | 一番単純で、検証しやすい。速くするのは動いてから |
| リフレッシュ | 8192 行 / 64 ms → 約 7.8 µs (50 MHz で 390 クロック) ごとにオートリフレッシュ。要求より優先 | 取りこぼすとデータが消える |
| 入出力 | アドレス・コマンド・データを IOB のフリップフロップで出し入れ | タイミングを安定させる (今のスラックは +0.395 ns と余裕が少ない) |
| バイト書き込み | DQM でバイト単位にマスク | SB / SH をそのまま扱える |

読み出しの遅れの見込み (50 MHz・データシート確認前の概算): 32 ビット幅なら 6〜7 クロック、
16 ビット × 2 回なら 7〜8 クロック。BSRAM の RAM (2 クロック) より 3〜4 倍遅いので、
スタックやよく使う変数は今の RAM に置いたままにし、SDRAM は大きなデータ用にする。

## Phase 1: シミュレーション用モデルとコントローラ単体

- `sim/models/sdram_model.v`: チップの振る舞いモデル (自作)。メモリ配列と、コマンドの順序・
  タイミング違反 (tRCD, tRP, tRC, リフレッシュ間隔の超過、初期化前のアクセス) を `$display` で報告して止める。
  メーカーのモデルはライセンスの確認が要るので、まず自作で始める
- `src/sdram_ctrl.v`: 初期化 (電源投入後 200 µs 待ち → プリチャージ → リフレッシュ 2 回 → モードレジスタ設定)、
  リフレッシュ、1 ワードの読み書き。CPU 側は `req / we / addr / wdata / be` → `ready / rdata` の簡単な口にする
- `sim/tb_sdram_ctrl.v`: ランダムなアドレス・データ・バイトマスクで書いて読み返し、比較する。
  リフレッシュとアクセスがぶつかる場合も流す

完了条件: tb_sdram_ctrl が PASS し、モデルがタイミング違反を 1 つも報告しない。

## Phase 2: 実機でコントローラ単体を確認 (CPU なし)

- テスト用トップ (`src/sdram_test_top.v`): 書き込み → 読み返しを全アドレスで繰り返す回路。
  パターンは「アドレスそのもの」「LFSR の乱数」「0 と 1 の交互」
- 結果をオンボード LED と UART (1 行ずつ: 通過回数とエラー数) に出す
- SDRAM へのクロックの位相を何通りか試し、エラーが 0 になる範囲の真ん中を選ぶ

完了条件: 全容量のテストを数十回まわしてエラー 0。

## Phase 3: SoC への組み込み

- `cpu_top.v` のアドレスデコードに SDRAM を足す
- **バスの待ち:** 今の SoC は「全スレーブが固定 1 サイクルで答える」前提。ハートは `dbus_gnt` と
  `dbus_rvalid` の待ちに対応済み (`BUS_STRESS` で確認済み) なので、変えるのは SoC 側:
  - ロードの応答 (`rsp_ok` / `dbus_rvalid`) を、SDRAM のときは `ready` まで待たせる
  - ストアも SDRAM が受け付けるまで `dbus_gnt` を出さない (コントローラに 1 段の書き込みバッファを置けば、
    すぐ受け付けて後で書ける。最初はバッファなしで単純に待たせる)
  - AMO / LR / SC の読み出し・演算・書き込み (`rmw_step`) を、SDRAM の待ちに合わせて進める
- 2 ハートからの同時アクセス: 今の調停 (ロード中はバスを占有、ラウンドロビン) のままでよい
- テストベンチ:
  - `sim/tb_sdram_soc.v`: CPU で SDRAM の読み書き・バイト/ハーフワード・符号拡張を自己検査
  - 2 ハートで SDRAM 上のカウンタを AMOADD / LR・SC で同時に更新 (`multicore_demo` の SDRAM 版)
  - 既存の全テストベンチが変わらず通ること (SDRAM を使わないプログラムに影響がないこと)

完了条件: 新旧すべてのテストベンチが PASS、合成で 50 MHz を満たす。

## Phase 4: ソフトウェア

- `tools/link.ld` に SDRAM の領域を足し、`__attribute__((section(".sdram")))` で配列を置けるようにする。
  `.sdram` は初期化しない (中身が要るならプログラムで書く)
- `examples/sdram_test.c`: 実機用のメモリテスト。Phase 2 のパターンに加え、バイト書き込み、
  2 ハート同時アクセス、AMO を確認し、UART に結果と速度 (MB/s) を出す
- README: メモリマップ、使い方、速度、ピン配置

完了条件: 実機で sdram_test が全項目 OK。

## Phase 5 以降 (任意。動いてから)

| 内容 | 効果 |
|:--|:--|
| 行を開いたままにする (同じ行への連続アクセスで ACTIVE を省く) | 連続アクセスが速くなる |
| 書き込みバッファ | ストアで待たなくなる |
| SDRAM を CPU より速いクロック (100 MHz など) で動かす | 帯域が増える。クロックの乗せ換え (非同期 FIFO) が要る |
| データキャッシュ (小さな直接マップ、BSRAM の残り 20 ブロックの一部) | 遅さをほぼ隠せる。2 ハートでの一貫性 (どちらかがキャッシュしない、など) を決める必要がある |
| 命令を SDRAM から取り出す + 命令キャッシュ + UART ブートローダ | 合成し直さずにプログラムを入れ替えられる。大きなプログラムを動かせる |
| オセロ AI の置換表を SDRAM に置く | 同じ局面を読み直さなくなり、同じ時間でより深く読める見込み |

## リスク

| リスク | 対策 |
|:--|:--|
| ピンが今の周辺と重なる | Phase 0 で確認し、A〜C から選ぶ |
| 実機でだけ化ける (クロックの位相・配線の長さ) | Phase 2 で CPU なしに確かめ、位相をパラメータで振る |
| 合成でタイミングが足りなくなる (今のスラック +0.395 ns) | SDRAM の口は必ずレジスタで区切り、デコードの経路を長くしない |
| リフレッシュの漏れ | モデルで間隔を検査する。実機テストを長時間 (数分) まわす |
| SoC の変更で既存の動作が壊れる | 既存の全テストベンチと `BUS_STRESS` のテストを毎回流す |
